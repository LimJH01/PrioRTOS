 \begin{quote}
{\bfseries{문서 상태\+:}} 이 문서의 아래 기존 절은 과거 {\ttfamily Ipcp\+Mutex\+\_\+t} 기반 구현의 변경 기록이다. 현재 기준 구현은 {\ttfamily \doxylink{mutex_8c}{kernel/mutex.\+c}}의 정적 {\ttfamily mutex\+\_\+t}와 {\ttfamily \doxylink{structTCB_a27fa4a29802a9290105f05aa4c837cac}{TCB\+\_\+t\+::held\+\_\+mutex}} 단일 소유권 모델이다. 현재 API는 {\ttfamily \doxylink{prio__rtos_8h_a7e920260b8ef52fb82798503b0b683eb}{mutex\+\_\+init(mutex\+\_\+t \texorpdfstring{$\ast$}{*}, uint8\+\_\+t)}}, {\ttfamily \doxylink{prio__rtos_8h_ab8962993baacb9669639c122ce4152f9}{mutex\+\_\+lock(mutex\+\_\+t \texorpdfstring{$\ast$}{*})}}, {\ttfamily \doxylink{prio__rtos_8h_aca4452a23a7c1e5e4399c55bc57c682b}{mutex\+\_\+unlock(mutex\+\_\+t \texorpdfstring{$\ast$}{*})}}이며, ID·사용자 bitmap·waiter handoff·동적 IPCP 설정 경로는 제거되었다. \end{quote}
이 문서는 IPCP 구현 작업에서 기존 코드의 어느 부분이 바뀌었는지, 새 코드가 어떤 책임을 맡는지, 모듈 간 동작이 어떻게 이어지는지 기록한다. 기록은 현재 작업 트리의 변경을 기준으로 하며, 이 문서가 추가된 시점의 구현은 빌드와 QEMU 기본 실행을 확인했지만 IPCP 전용 자동 테스트는 아직 없다.\hypertarget{md_docs_2ipcp-change-record_autotoc_md37}{}\doxysection{\texorpdfstring{1. 변경 요약}{1. 변경 요약}}\label{md_docs_2ipcp-change-record_autotoc_md37}
기존에는 {\ttfamily \doxylink{mutex_8c}{mutex.\+c}}가 동적 할당이 아닌 고정 크기 테이블에서 mutex를 생성하고 기본적인 잠금, 차단, 소유권 인계를 수행했다. mutex마다 ceiling과 사용 태스크 목록은 없었고, 태스크의 {\ttfamily priority}가 ready bitmap 인덱스처럼도 사용되고 있어 유효 우선순위가 바뀌는 IPCP 동작과 직접 연결되지 않았다.

이번 변경에서는 mutex 구현을 {\ttfamily ipcp.\+c}로 옮기고 정적 ID 및 사전 등록한 사용자 슬롯 비트맵을 사용하도록 했다. 등록 시 사용 태스크들의 기본 우선순위로 ceiling을 계산한다. lock은 자원 가용성과 system ceiling을 확인하고, 현재 태스크가 획득할 수 없는 경우 mutex의 대기자 bitmap에 슬롯을 기록한 뒤 BLOCKED 상태로 만든다. lock 획득/해제 및 소유권 이전에 맞춰 TCB의 유효 우선순위를 갱신한다.

유효 우선순위가 같아지는 상황을 금지하지 않는다. 스케줄러는 현재 태스크보다 숫자가 작은 유효 우선순위가 있을 때만 선점한다. 현재 태스크가 더 이상 RUNNING이 아니면 숫자가 가장 작은 유효 우선순위를 선택하고, 우선순위 동률에서는 슬롯 번호가 작은 태스크를 결정적인 기준으로 삼는다. 우선순위별 FIFO ready queue는 이번 변경에 포함하지 않았다.\hypertarget{md_docs_2ipcp-change-record_autotoc_md38}{}\doxysection{\texorpdfstring{2. 파일별 변경 내용}{2. 파일별 변경 내용}}\label{md_docs_2ipcp-change-record_autotoc_md38}
\hypertarget{md_docs_2ipcp-change-record_autotoc_md39}{}\doxysubsection{\texorpdfstring{2.\+1 $<$tt$>$kernel/ipcp.\+c$<$/tt$>$ — IPCP 구현 모듈 신규 추가}{2.1 <tt>kernel/ipcp.c</tt> — IPCP 구현 모듈 신규 추가}}\label{md_docs_2ipcp-change-record_autotoc_md39}
새 파일은 mutex 설정과 IPCP 실행 상태를 한 곳에서 관리한다. 동적 메모리 할당 없이 {\ttfamily MAX\+\_\+\+MUTEXES} 크기의 정적 배열을 사용한다.\hypertarget{md_docs_2ipcp-change-record_autotoc_md40}{}\doxysubsubsection{\texorpdfstring{내부 mutex 상태}{내부 mutex 상태}}\label{md_docs_2ipcp-change-record_autotoc_md40}
각 mutex 항목은 다음 상태를 가진다.


\begin{DoxyItemize}
\item {\ttfamily configured}\+: 해당 고정 ID가 초기화 때 설정되었는지 여부
\item {\ttfamily locked}, {\ttfamily owner\+\_\+slot}\+: 현재 잠금 상태와 소유 태스크 슬롯
\item {\ttfamily user\+\_\+slots}\+: lock이 허용된 태스크 슬롯을 나타내는 비트맵
\item {\ttfamily waiters}\+: 해당 mutex를 기다리며 BLOCKED된 태스크 슬롯 비트맵
\item {\ttfamily ceiling}\+: 사용자 태스크의 {\ttfamily base\+\_\+priority} 최솟값으로 계산한 자원 ceiling(숫자가 작을수록 높은 우선순위)
\end{DoxyItemize}

별도의 {\ttfamily configuration\+\_\+frozen} 플래그를 두고 스케줄러 시작 이후 mutex 설정 변경을 차단한다.\hypertarget{md_docs_2ipcp-change-record_autotoc_md41}{}\doxysubsubsection{\texorpdfstring{태스크 및 ceiling 처리}{태스크 및 ceiling 처리}}\label{md_docs_2ipcp-change-record_autotoc_md41}

\begin{DoxyItemize}
\item {\ttfamily current\+\_\+task\+\_\+slot()}은 {\ttfamily g\+\_\+current\+\_\+tcb}가 \doxylink{structTCB}{TCB} 배열의 어느 슬롯을 가리키는지 확인하고, 현재 상태가 RUNNING인지 함께 검사한다.
\item {\ttfamily configured\+\_\+user\+\_\+mask()}는 idle 슬롯 0과 {\ttfamily MAX\+\_\+\+TASKS} 범위 밖 비트를 허용하지 않는 마스크를 만든다. 최대 32 슬롯일 때 shift overflow가 나지 않도록 32 슬롯 경우를 따로 처리한다.
\item {\ttfamily system\+\_\+ceiling(requesting\+\_\+slot)}은 요청 태스크가 소유하지 않은, 현재 잠긴 mutex의 ceiling 최솟값을 구한다. 잠긴 자원이 하나도 없을 때는 {\ttfamily UINT32\+\_\+\+MAX}를 반환해 ceiling 제한이 없음을 표시한다.
\item {\ttfamily refresh\+\_\+effective\+\_\+priority(slot)}은 태스크의 기본 우선순위와 현재 보유한 모든 mutex의 ceiling 중 최솟값을 다시 계산해 {\ttfamily \doxylink{structTCB_a658a5617296ad7a4209695d613b518b7}{TCB\+\_\+t.\+priority}}에 저장한다. mutex 하나를 해제해도 더 높은 ceiling(더 작은 숫자)의 다른 mutex가 남아 있으면 그 ceiling을 유지하며, 더 이상 보유 mutex가 없으면 기본 우선순위로 복귀한다.
\item {\ttfamily can\+\_\+acquire()}는 요청 mutex가 설정되었고, 잠기지 않았으며, 호출 태스크가 사용자 목록에 들어 있는지 확인한다. 이어서 호출 태스크의 유효 우선순위가 다른 태스크들이 보유한 system ceiling보다 엄격히 높은지 검사한다.
\end{DoxyItemize}\hypertarget{md_docs_2ipcp-change-record_autotoc_md42}{}\doxysubsubsection{\texorpdfstring{정적 설정 API}{정적 설정 API}}\label{md_docs_2ipcp-change-record_autotoc_md42}
{\ttfamily mutex\+\_\+configure(mutex\+\_\+id, user\+\_\+slots)}는 공개 mutex 설정 API다.


\begin{DoxyEnumerate}
\item ID가 {\ttfamily 0..MAX\+\_\+\+MUTEXES-\/1}인지 확인한다.
\item 사용자 비트맵이 0이 아니고 idle 슬롯/미사용 상위 비트를 포함하지 않는지 확인한다.
\item 인터럽트를 보호한 상태에서 설정이 아직 동결되지 않았는지, 같은 ID를 이미 설정하지 않았는지 검사한다.
\item 각 지정 슬롯에 태스크가 실제 등록되어 있는지 확인한다.
\item 지정된 태스크들의 {\ttfamily base\+\_\+priority} 최솟값을 ceiling으로 계산하고 mutex 항목을 설정한다.
\end{DoxyEnumerate}

실패 시 구체적인 {\ttfamily Mutex\+Result\+\_\+t} 오류 코드를 반환하며 해당 mutex 설정을 성공 상태로 만들지 않는다. 설정은 {\ttfamily \doxylink{prio__rtos_8h_a5d79d14e4f5972ce977309150daf4f06}{priortos\+\_\+start()}}가 호출되기 전에 이루어져야 한다.\hypertarget{md_docs_2ipcp-change-record_autotoc_md43}{}\doxysubsubsection{\texorpdfstring{lock, block, 재개 처리}{lock, block, 재개 처리}}\label{md_docs_2ipcp-change-record_autotoc_md43}
{\ttfamily mutex\+\_\+lock(mutex\+\_\+id)}는 잘못된 ID, 미설정 mutex, 잘못된 호출 문맥, 비사용자 태스크, 재귀 잠금을 검사한다.


\begin{DoxyItemize}
\item 자원이 비어 있고 system-\/ceiling 조건도 만족하면 현재 슬롯을 소유자로 설정하고 effective priority를 즉시 재계산한 뒤 {\ttfamily MUTEX\+\_\+\+OK}를 반환한다.
\item 자원이 사용 중이거나 ceiling 조건을 통과하지 못하면 호출 태스크의 슬롯 비트를 해당 mutex의 waiter bitmap에 넣고 {\ttfamily \doxylink{kernel__internal_8h_a4d7dab794c442854eb0b8740d420bb7e}{sched\+\_\+block\+\_\+current()}}로 현재 태스크를 BLOCKED 처리한다.
\item 대기 태스크가 소유권을 이전받아 다시 스케줄되면 {\ttfamily \doxylink{prio__rtos_8h_ab8962993baacb9669639c122ce4152f9}{mutex\+\_\+lock()}}의 반복문이 다시 실행된다. mutex가 이미 자기 슬롯 소유로 넘어온 것을 확인하고 {\ttfamily MUTEX\+\_\+\+OK}를 반환한다.
\item 같은 태스크가 lock 호출을 재개하기 전에 동일 waiter로 중복 등록되는 상태는 {\ttfamily MUTEX\+\_\+\+ERR\+\_\+\+INVALID\+\_\+\+WAITER}로 거부한다.
\end{DoxyItemize}

대기 태스크가 실제로 block된 뒤 재개했을 때 소유권을 확인하는 동작은 mutex handoff가 잠금 반환보다 먼저 완료되는 모델이다.\hypertarget{md_docs_2ipcp-change-record_autotoc_md44}{}\doxysubsubsection{\texorpdfstring{unlock 및 waiter handoff}{unlock 및 waiter handoff}}\label{md_docs_2ipcp-change-record_autotoc_md44}
{\ttfamily mutex\+\_\+unlock(mutex\+\_\+id)}는 현재 태스크가 실제 소유자인지 검사한다. 비소유자나 잘못된 문맥에서의 호출은 mutex 상태를 바꾸지 않고 오류를 반환한다. 정상 unlock은 다음 순서로 수행한다.


\begin{DoxyEnumerate}
\item 현재 mutex의 잠금과 소유자를 해제한다.
\item 이전 소유자의 effective priority를 나머지 보유 mutex ceiling을 고려해 재계산한다.
\item {\ttfamily dispatch\+\_\+eligible\+\_\+waiters()}로 잠금 가능한 waiter를 다시 평가한다.
\item 선택한 waiter를 새 소유자로 먼저 기록하고, waiter bitmap에서 제거하고, effective priority를 갱신한 뒤 READY로 깨운다.
\item 더 이상 적격 waiter가 없을 때까지 반복한다. 다른 mutex의 ceiling 때문에 아직 대기해야 하는 태스크는 BLOCKED로 남겨 다음 unlock에서 다시 검사한다.
\item MSIP를 요청하고 인터럽트를 복구해 더 높은 우선순위 태스크가 준비되었다면 스케줄러가 실행하도록 한다.
\end{DoxyEnumerate}

대기자 순위는 effective priority 오름차순(숫자가 작은 순서), 동률이면 슬롯 번호 오름차순이다. 소유권은 wakeup보다 먼저 기록하여 waiter가 READY가 된 뒤 소유자 없는 mutex를 관찰하지 않도록 한다. 내부 waiter 상태가 \doxylink{structTCB}{TCB} 상태와 불일치하면 {\ttfamily kernel\+\_\+panic()}으로 커널 오류를 드러낸다.\hypertarget{md_docs_2ipcp-change-record_autotoc_md45}{}\doxysubsubsection{\texorpdfstring{부팅 설정 검증과 동결}{부팅 설정 검증과 동결}}\label{md_docs_2ipcp-change-record_autotoc_md45}

\begin{DoxyItemize}
\item {\ttfamily ipcp\+\_\+validate\+\_\+configuration()}는 시작 시 등록된 mutex마다 사용자 비트가 유효하고 지정된 슬롯에 태스크가 존재하는지 확인한다.
\item {\ttfamily ipcp\+\_\+scheduler\+\_\+started()}는 첫 태스크 선택을 마친 뒤 설정을 동결한다.
\end{DoxyItemize}\hypertarget{md_docs_2ipcp-change-record_autotoc_md46}{}\doxysubsection{\texorpdfstring{2.\+2 $<$tt$>$kernel/sched.\+c$<$/tt$>$ — 슬롯 bitmap과 유효 우선순위 스케줄링 연결}{2.2 <tt>kernel/sched.c</tt> — 슬롯 bitmap과 유효 우선순위 스케줄링 연결}}\label{md_docs_2ipcp-change-record_autotoc_md46}
\hypertarget{md_docs_2ipcp-change-record_autotoc_md47}{}\doxysubsubsection{\texorpdfstring{최고 우선순위 태스크 선택 변경}{최고 우선순위 태스크 선택 변경}}\label{md_docs_2ipcp-change-record_autotoc_md47}
기존에는 ready bitmap의 set bit를 슬롯 순회하며 각 TCB의 {\ttfamily priority}(유효 우선순위)를 비교했다. 현재 {\ttfamily sched\+\_\+highest\+\_\+priority\+\_\+slot(task\+\_\+bitmap)}은 직접 매핑 규칙에 따라 최하위 set bit를 De Bruijn LUT로 O(1)에 추출한다.


\begin{DoxyItemize}
\item bitmap은 task slot을 식별하는 용도로만 사용한다.
\item 최하위 set bit, 즉 숫자가 가장 작은 직접 매핑 priority가 우선 선택된다.
\item 비교 우선순위가 같으면 이미 선택된 더 작은 슬롯을 그대로 유지한다.
\item 함수 반환값은 우선순위 값이 아니라 {\ttfamily g\+\_\+tcbs\mbox{[}\mbox{]}} 인덱스다. 준비 슬롯이 없으면 {\ttfamily MAX\+\_\+\+TASKS}를 반환한다.
\end{DoxyItemize}

\begin{DoxyEnumerate}
\item 태스크가 {\ttfamily mutex\+\_\+lock(id)}를 호출한다.
\item 호출 태스크의 배열 슬롯과 RUNNING 상태, 설정된 사용자 여부를 검사한다.

\item 소유 자원 ceiling을 기준으로 caller의 effective priority를 다시 계산한다.
\item {\ttfamily mutex\+\_\+unlock(id)}는 현재 소유자만 수행할 수 있다.

\item {\ttfamily MAX\+\_\+\+TASKS}를 8보다 크게 확장하지 않았다. 기존 slot bitmap 기반 구조와 task 생성 API의 범위는 별도 요구사항 변경이 필요하다.

\item 보드 대상 WCET, timer latency 또는 IPCP blocking bound를 측정/증명하지 않았다.
\item 기존 basic mutex의 {\ttfamily mutex\+\_\+create()} API와 동적 ID 배정 호환성을 유지하지 않았다.
