# PrioRTOS 요구사항 초안

## 문서 상태

- 상태: 초안
- 목적: 구현 및 테스트의 기준을 합의하기 위한 요구사항 목록
- 주의: 이 문서는 인증 완료, Hard RTOS 보장 또는 정형 검증 완료를 주장하지 않는다.
- 미결정 설계 선택은 [design-decisions.md](./design-decisions.md)에 기록한다.

요구사항 상태:

- `확정(코드 관찰)`: 현재 소스에서 값이나 구조를 확인했으나, 그 자체로 검증 완료를 뜻하지 않는다.
- `제안`: 초기 구현을 위한 권고안이며, 사용자 확인 후 확정한다.
- `미결정`: 구현 전에 결정해야 한다.

## 1. 목표와 범위

### 목표

PrioRTOS는 정적으로 구성된 태스크를 실행하고, 우선순위 기반 선점 스케줄링과 Immediate Priority Ceiling Protocol(IPCP)을 제공하는 단일 hart RISC-V RTOS를 목표로 한다. 커널의 핵심 실행 경로는 유계 실행시간을 갖도록 설계하고, 대상 하드웨어에서 측정·검증한다.

### 초기 범위 제안

- QEMU `virt`에서 기능 개발 및 반복 테스트
- RV32 단일 hart, Machine Mode 우선 지원
- 고정된 태스크 집합과 정적 스택
- 고정 우선순위 선점 스케줄링
- IPCP 뮤텍스 및 명시적인 대기/깨우기 상태 전이
- 동적 힙, 멀티코어, 메모리 보호, 실제 항공·방산 안전 인증은 초기 범위에서 제외

실제 보드 지원과 더 강한 안전성 주장은 별도 검증 범위로 다룬다.

## 2. 현재 코드에서 확인한 기준선

| 항목 | 현재 확인된 내용 | 요구사항 상태 |
|---|---|---|
| CPU ISA | Makefile이 `rv32i_zicsr`와 `ilp32`를 지정 | 확정(코드 관찰) |
| 실행 환경 | QEMU `virt` 실행 타깃이 있음 | 확정(코드 관찰); 실제 보드 지원 여부는 미결정 |
| hart 수 | 멀티코어 지원 코드가 보이지 않음 | 단일 hart 제안 |
| 태스크 최대 수 | `MAX_TASKS`가 8 | 확정(코드 관찰) |
| 우선순위 범위 | 0..7, 숫자가 큰 값이 더 높은 우선순위로 선택됨 | 확정(코드 관찰) |
| 우선순위 중복 | 현재 `task_create`는 우선순위당 태스크 하나만 허용 | 확정(코드 관찰); 정책 유지 여부 미결정 |
| 태스크/스택 할당 | 앱에서 스택 배열을 정적으로 선언하고 부팅 중 `task_create` 호출 | 확정(코드 관찰); 빌드 시 생성으로 바꿀지 미결정 |
| 타이머 | CLINT `mtime`/`mtimecmp` 접근 코드가 있음 | 확정(코드 관찰) |
| 타이머 주기 | 주석의 10 MHz 및 `10,000,000` interval은 1초에 해당하나 주석 일부는 1 ms라 설명이 불일치 | 미결정; 반드시 합의 후 수정 |
| IPCP | 뮤텍스 API 선언은 있으나 `mutex.c` 구현은 비어 있음 | 미구현 |
| 검증 | 저장소에 실제 테스트/정형검증 파일이 확인되지 않음 | 미구현 |

## 3. 기능 요구사항

각 요구사항은 연결된 테스트가 작성되고 통과한 뒤에만 `검증 완료`로 표시한다. 구조적 복잡도만으로 실제 시간 상한을 입증했다고 간주하지 않는다.

| ID | 요구사항 | 검증 기준 | 현재 상태 |
|---|---|---|---|
| `SYS-001` | 커널은 승인된 대상 설정으로 빌드되어야 한다. | 고정된 툴체인/플래그로 깨끗한 빌드가 성공하고 QEMU에서 부팅한다. | 부분 구현 |
| `SYS-002` | 초기 릴리스는 합의된 hart 수와 privilege mode에서 동작해야 한다. | 문서화한 설정에서 부팅·인터럽트·태스크 전환 테스트를 통과한다. | 단일 hart 제안 |
| `TASK-001` | 커널은 최대 8개 태스크를 관리한다. | 허용된 수의 등록이 성공하고 초과 등록은 명시적 오류로 거부된다. | 부분 구현 |
| `TASK-002` | 태스크의 스택은 정적으로 제공되며 커널은 힙 할당에 의존하지 않는다. | 링크된 이미지와 소스에서 커널 동적 할당 의존성이 없음을 확인한다. | 부분 구현 |
| `TASK-003` | 태스크 설정 오류는 태스크를 실행하기 전에 감지되어야 한다. | null 포인터, 범위 오류, 중복 ID/우선순위, 스택 크기/정렬 오류별 오류 테스트가 통과한다. | 부분 구현 |
| `TASK-004` | 태스크 상태는 `UNUSED`, `READY`, `RUNNING`, `BLOCKED` 사이에서 정의된 전이만 허용한다. | 각 허용·불허 전이 및 ready 자료구조의 일관성을 단위 테스트한다. | 미구현 |
| `SCHED-001` | 스케줄러는 실행 가능한 태스크 중 가장 높은 우선순위 태스크를 선택한다. | 여러 우선순위 조합에서 선택 결과가 규칙과 일치한다. | 부분 구현 |
| `SCHED-002` | ready 태스크가 없을 때는 정의된 idle 동작을 수행한다. | 모든 태스크를 블록한 경우 idle 태스크가 실행되고 인터럽트로 정상 복귀한다. | 미구현 |
| `SCHED-003` | ready 태스크의 삽입/제거와 현재 태스크 변경은 원자적으로 관리된다. | 인터럽트 경계와 API 경계에서 상태·비트맵 불변식을 검사한다. | 미구현 |
| `SCHED-004` | 태스크 선택의 알고리즘 복잡도는 태스크 개수에 의존하지 않는 O(1)이어야 한다. | 구현 경로에 태스크 전체 검색이 없는지 검토하고 타깃 실행시간을 측정한다. | 설계 의도, 미검증 |
| `TIME-001` | 타이머 timebase, 단위 및 주기는 명시된 설정과 일치해야 한다. | 설정값에서 계산한 주기와 하드웨어 측정 결과가 정한 허용 오차 안에 든다. | 미결정/불일치 |
| `TIME-002` | 블록된 태스크는 지정된 시각 또는 이벤트에서만 다시 준비 상태가 된다. | 경계 시각, 동시 만료, 오버플로 조건에 대한 테스트가 통과한다. | 미구현 |
| `TIME-003` | 태스크별 period, deadline, WCET 요구는 시스템 구성에 기록한다. | 구성 검증기가 필수값 누락과 불일치를 시작 전에 거부한다. | 미결정 |
| `IPC-001` | 각 자원은 정적으로 정의되고 유효한 ceiling을 가져야 한다. | 태스크-자원 사용표에서 계산한 ceiling과 설정이 일치하며, 잘못된 설정은 거부된다. | 미구현 |
| `IPC-002` | 뮤텍스 획득/해제는 선택된 IPCP 정의를 준수해야 한다. | 자원 경쟁, 중첩 자원, 비소유자 해제 등 정의된 시나리오를 테스트한다. | 미구현 |
| `IPC-003` | IPCP에서 태스크의 유효 우선순위는 보유 자원 및 프로토콜 규칙과 일치해야 한다. | lock/unlock 각 단계의 effective priority와 스케줄 결과를 검증한다. | 미구현 |
| `IPC-004` | 뮤텍스 획득이 즉시 불가능할 때의 대기/오류 동작은 명시되어야 한다. | 차단 정책과 잘못된 호출에 대한 결과를 테스트한다. | 미결정 |
| `TRAP-001` | 지원하는 인터럽트/예외만 처리하고, 지원하지 않는 원인은 정의된 오류 경로로 보낸다. | 각 지원·미지원 `mcause`를 주입하거나 재현해 예상 경로를 확인한다. | 부분 구현 |
| `TRAP-002` | 인터럽트 문맥 저장·복원은 모든 태스크 레지스터 및 복귀 상태를 보존한다. | 레지스터 패턴 테스트와 반복 선점 테스트를 통과한다. | 구현 존재, 미검증 |
| `ERR-001` | 스택 가드 손상은 감지되고 정상 스케줄링을 중단하는 명시적 오류 경로로 이어진다. | 가드 손상 시 panic 경로가 실행되는지 확인한다. | 부분 구현 |
| `ERR-002` | 커널 panic은 추가 인터럽트를 차단하고 정의된 정지/안전 동작을 수행한다. | panic 원인별로 인터럽트 차단, 진단, 후속 동작을 확인한다. | 부분 구현 |
| `ERR-003` | deadline miss 처리 정책은 안전 요구에 맞게 명시되어야 한다. | miss를 의도적으로 발생시켜 기록·알림·정지 등 정책을 검증한다. | 미결정 |

## 4. 시간 결정성 및 검증 요구사항

| ID | 요구사항 | 검증 기준 |
|---|---|---|
| `TIME-DET-001` | 스케줄러, IPCP, 트랩 처리의 시간 측정 범위와 측정 방법을 명시한다. | 타깃에서 최악 조건을 포함한 반복 측정 결과와 측정 한계를 기록한다. |
| `TIME-DET-002` | 각 핵심 경로의 WCET 상한은 애플리케이션의 deadline 요구보다 작아야 한다. | WCET 분석/측정값을 response-time 또는 동등한 분석에 반영하고 deadline을 만족한다. |
| `TIME-DET-003` | 인터럽트 비활성 구간은 유한하고 상한을 측정할 수 있어야 한다. | 최대 비활성 사이클 수를 계측하고 요구 상한과 비교한다. |
| `TEST-001` | 모든 기능 요구사항은 하나 이상의 테스트 또는 분석 항목에 연결되어야 한다. | 요구사항-코드-테스트 추적표에서 누락 항목이 없다. |
| `TEST-002` | 테스트는 정상 경로뿐 아니라 경계/오류 조건도 포함해야 한다. | 검토된 테스트 계획과 자동화 결과를 보관한다. |
| `TEST-003` | QEMU 검증과 실제 하드웨어 시간 검증 결과를 구분한다. | 각 결과물에 대상, 설정, 도구 버전 및 실행 조건이 기록된다. |

## 5. 초기 수용 기준 제안

아래 기준은 프로토타입 종료 기준으로 제안한다. 제품 또는 안전 요구사항으로 사용하기 전에 수치와 정책을 확정해야 한다.

1. QEMU에서 깨끗한 빌드 후 반복 부팅할 수 있다.
2. 고정 태스크 구성이 시작 전에 검증되고, 잘못된 구성은 실행 전에 식별된다.
3. READY/RUNNING/BLOCKED 전이가 테스트되고, 준비된 태스크 중 우선순위 규칙에 맞는 태스크가 선택된다.
4. 지정한 주기의 타이머가 동작하고, 블록된 태스크가 정해진 시점에 다시 준비된다.
5. IPCP 정상·경계·오류 시나리오가 테스트되며, 유효 우선순위와 자원 소유권 불변식이 유지된다.
6. 반복 선점 및 장시간 QEMU 통합 테스트에서 커널 상태 손상이나 예상 밖의 task starvation이 관찰되지 않는다.
7. O(1) 알고리즘 구조와 실제 타깃의 실행시간 측정 결과를 별도로 제시한다. 둘 중 하나만으로 시간 결정성을 주장하지 않는다.

## 6. 요구사항 변경 절차

1. 설계 선택을 [design-decisions.md](./design-decisions.md)에 기록한다.
2. 요구사항 표의 `미결정` 항목을 결정하고 담당자/날짜를 남긴다.
3. 요구사항 ID를 구현 코드와 테스트에 연결한다.
4. 구현·테스트가 합의된 기준을 통과한 뒤 상태를 갱신한다.
5. 대상 CPU, 보드, 컴파일러 또는 타이밍 설정이 바뀌면 영향받는 요구사항과 테스트를 재검토한다.
